# 用户注册登录改造设计

> 本文记录注册改造时的决策。当前接口、注册模式和行为以 [API 设计](API设计.md)为准。

> 状态：已实现（2026-08-17）。本文是本轮改造的设计依据；落地后的正式契约以 `docs/API设计.md`、`docs/数据库设计.md` 为准。

## 1. 背景与目标

当前系统是纯"后台开号"模式：没有自助注册入口，所有账号必须由 `admin` 通过后台管理接口创建，登录只支持用户名 + 密码。

本轮改造目标：在**保留现有测试账号（用户名 + 密码）完全可用**的前提下，新增手机号或邮箱 + 密码的自助注册与登录能力。

## 2. 已确认的关键决策

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 是否需要短信/邮箱验证码 | **不需要，注册即激活** | 当前系统未接入任何短信网关或 SMTP 服务，接入会显著增加复杂度和运营成本；项目定位是课题组内部工具，可接受先不做真实性校验，后续如需对外开放可再补 |
| 注册入口范围 | **完全开放自助注册** | 项目当前没有公网暴露的注册入口，先做最简单的开放注册；后续如需收紧可加邀请码机制 |
| 手机号格式 | **仅支持中国大陆手机号** | `^1[3-9]\d{9}$`，与现有 `phone` 字段历史数据格式一致 |
| 密码策略 | 最少 8 位，最多 72 字节（bcrypt 上限） | 无复杂度强制要求，与 admin 建号路径的密码校验对齐 |
| 新用户角色 | 服务端强制写死 `member` | 客户端请求体不接受 `role` 字段，防止越权注册管理员账号 |
| 用户名字段 | 自助注册用户不设用户名（`username` 为 NULL） | 用户明确只要求"手机号或邮箱+密码"，不引入额外的用户名输入项 |

**明确排除范围**（本轮不做）：短信/邮箱验证码、邀请码/邀请链接、找回密码。

## 3. 数据模型变更

新增迁移 `backend-go/migrations/010_self_registration.sql`：

```sql
ALTER TABLE users ALTER COLUMN username DROP NOT NULL;

CREATE UNIQUE INDEX IF NOT EXISTS idx_users_email_unique ON users (email) WHERE email IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_phone_unique ON users (phone) WHERE phone IS NOT NULL;
```

- `username` 从 `NOT NULL` 改为可空：Postgres 的 `UNIQUE` 约束默认视多个 `NULL` 为互不相同，因此老账号（有用户名）不受影响，自助注册用户（无用户名）也不会互相冲突。
- `email`/`phone` 各加**部分唯一索引**（`WHERE ... IS NOT NULL`），只在非空时强制唯一，不影响历史上 email/phone 为空的账号。
- **前置核实**（已于设计阶段完成，非开发时再查）：当前生产库 7 个用户，email/phone 均无重复值，可安全直接加索引，无需数据清洗步骤。

## 4. API 契约变更

### 4.1 新增 `POST /api/v1/auth/register`（公开路由）

请求体：

```json
{
  "email": "user@example.com",
  "phone": "13800138000",
  "password": "至少8位",
  "display_name": "显示姓名"
}
```

- `email`、`phone` 至少填一项，可都填。
- 校验失败返回 `400 validation_error`；`email`/`phone` 已被占用返回 `409 conflict`，错误信息区分"该邮箱已被注册"/"该手机号已被注册"（通过 Postgres 唯一索引冲突时的 `pq.Error.Constraint` 字段精确判断是哪个索引冲突，而不是笼统提示）。
- 成功响应与登录接口同构，**注册成功即签发 JWT 自动登录**：

```json
{
  "data": {
    "access_token": "...",
    "token_type": "Bearer",
    "expires_in": 7200,
    "user": { "id": "...", "username": "", "display_name": "...", "role": "member" }
  }
}
```

- 挂独立限流：新增 `REGISTER_RATE_LIMIT_PER_MIN` 环境变量（默认建议 5/分钟/IP），复用现有 `middleware.RateLimiter`，与登录限流互不共享计数桶。

### 4.2 改造 `POST /api/v1/auth/login`

- 请求体字段 `username` 更名为 `identifier`（前端同步改名，无外部 API 消费方，改名安全）。
- 后端查询逻辑从"仅按 username 精确匹配"改为 `WHERE username = $1 OR email = $1 OR phone = $1`，同一个入口三选一登录。
- 老测试账号（只有 username，无 email/phone）行为完全不变；新注册账号（只有 email/phone，无 username）用注册时填的手机号或邮箱登录。

### 4.3 `/auth/me`（GET/PATCH）

不改动。已支持的 `display_name`/`email`/`phone`/`wechat` 自助维护字段对新老账号都适用；账号标识、角色、状态仍只读。

## 5. 后端实现要点（文件级改动清单）

| 文件 | 改动 |
| --- | --- |
| `backend-go/migrations/010_self_registration.sql` | 新增，见第 3 节 |
| `internal/domain/auth/types.go` | `UserRecord` 新增 `Username string` 字段（当前完全没有该字段，`AuthService.Login` 目前是拿"用户输入的登录标识符"顶替真实用户名塞进 JWT，改造后必须用数据库里的真实值，否则手机号/邮箱登录时会把手机号错误地当成 username 存进 JWT）；新增 `RegisterUserInput{Email, Phone, PasswordHash, DisplayName}` |
| `internal/repository/contracts.go` | `UserAuthReader` 接口：`FindUserByUsername` 更名为 `FindUserByIdentifier`；新增 `RegisterUser(ctx, auth.RegisterUserInput) (*auth.UserRecord, error)` |
| `internal/repository/postgres/user_auth_repository.go` | 实现上述接口变更；`FindUserByIdentifier` 查询条件改为三选一 `OR`；新增 `RegisterUser`（`INSERT ... email = NULLIF($,''), phone = NULLIF($,'')`，冲突时用 `pq.Error.Constraint` 精确返回哪个字段冲突）；**`GetUserProfile`/`UpdateUserProfile` 的 `SELECT username` 必须改成 `COALESCE(username, '')`**——这是 username 允许为 NULL 后的必然连锁修复，否则自助注册用户查自己 profile 会因 Scan NULL 到 string 直接报错崩溃 |
| `internal/repository/memory/user_auth_repository.go` | 当前是固定单一开发管理员账号的静态 fixture，不支持动态建号。需要改造为 `sync.RWMutex` + map 的有状态实现（参考 `data_asset_repository.go` 的既有模式），保留默认开发管理员账号，同时支持 `RegisterUser` 动态添加、`FindUserByIdentifier` 按用户名/邮箱/手机号查找。**必须做**：`handlers_test.go` 通过 `bootstrap.BuildContainer` 走的正是 memory 模式，注册相关的 handler 集成测试依赖这个实现 |
| `internal/service/auth_service.go` | `Login` 改为按 identifier 查找，claims 使用 `user.Username`（数据库真实值）而非入参；新增 `Register` 方法：校验 email/phone 至少一项、密码长度 8–72、中国大陆手机号正则、邮箱基础格式校验、display_name 非空且 ≤64 字符，校验通过后 bcrypt 哈希密码、调用 `RegisterUser`、签发 JWT 并返回（与 Login 共享"生成 claims + 签发 token"的收尾逻辑，可抽成私有辅助函数复用） |
| `internal/transport/http/request/*.go` | `LoginRequest.Username` 更名为 `Identifier`；新增 `RegisterRequest{Email, Phone, Password, DisplayName}` |
| `internal/transport/http/handlers/auth.go` | `Login` 改用 `payload.Identifier`；新增 `Register` handler，校验错误走 `writeServiceError`（`ErrValidation`→400，`ErrConflict`→409），成功走和 `Login` 相同的响应体拼装（可抽共享函数） |
| `internal/config/config.go` | 新增 `RegisterRateLimitPerMin int`，`getEnvInt("REGISTER_RATE_LIMIT_PER_MIN", 5)` |
| `internal/transport/http/router/router.go` | 公开路由区新增 `POST /auth/register`，独立 `registerLimiter := middleware.NewRateLimiter(cfg.RegisterRateLimitPerMin, time.Minute)` |
| `.env.example` / `.env.production.example` | 补充 `REGISTER_RATE_LIMIT_PER_MIN` 说明 |

## 8. 风险与注意事项

- **claims.Username 语义修正**是本轮一个隐藏的正确性修复，不只是新功能：现状下用手机号登录会把手机号误当用户名塞进 JWT 和前端展示，必须顺带修掉。
- **memory 后端改造**范围比表面看起来大：从"零状态固定 fixture"变成"有状态可写存储"，改动集中在 `internal/repository/memory/user_auth_repository.go` 一个文件内，不影响其他 memory 仓储实现。
- 唯一索引使用 `pq.Error.Constraint` 而非现有 `isUniqueViolation`（字符串匹配 `23505`）辅助函数，因为需要精确区分是哪个字段冲突以给出友好提示；不改动 `isUniqueViolation` 本身，保留给其他仍用得到的地方。
