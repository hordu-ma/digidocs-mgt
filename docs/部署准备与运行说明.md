# DigiDocs Mgt 部署准备与运行说明

## 1. 目标

本文档描述两件事：

- 本项目仓库内已经具备的部署资产；
- 当前推荐的目标部署分层与启动顺序。

外部前提：

- OpenClaw Gateway 已在目标机器上安装并可通过 HTTP API 访问；
- Synology DSM / File Station API 已准备好服务账号与共享目录；
- PostgreSQL 已确定运行位置与备份策略。

## 2. 目标部署分层

当前推荐按三层理解正式部署：

1. 应用层
  - 机器：`DGX Spark`
  - 承载：`frontend`、`backend-go`、`backend-py-worker`、反向代理、OpenClaw Gateway
2. 数据库层
  - 机器：`群晖 DS925+`
  - 承载：`PostgreSQL`
  - 推荐方式：使用群晖 `Container Manager` 运行数据库容器
3. 文件层
  - 机器：`群晖 DS925+`
  - 承载：DSM / File Station / 共享目录 / 快照 / 权限 / 备份等原生能力

说明：

- 群晖文件层优先复用 DSM 原生服务，不建议为了形式统一再额外容器化一套文件服务；
- 仓库根目录现有 [docker-compose.yml](../docker-compose.yml) 主要用于单机开发联调，不等同于最终双节点部署形态。

### 2.0 访问入口与部署后检查（2026-11-10）

- 公网：`http://8.152.204.76`（经 frp 转发到本机前端）。
- 本机：`http://127.0.0.1:18080`。前端端口只绑定回环地址，局域网其他电脑不能直接用本机局域网 IP 加 18080 访问，请使用公网地址。
- 每次部署后执行 `PUBLIC_URL=http://8.152.204.76 make post-deploy-check`。它沿用户真实路径（前端 nginx 到后端）检查，而不是只看容器健康或直连后端 18081。
- 2026-11-10 事故：前端 nginx 原先只在启动时解析一次后端地址，后端容器重建换 IP 后，所有 API 经前端返回 502，而容器健康检查和直连后端检查全部正常。现已改为经 Docker 内置 DNS（`resolver 127.0.0.11 valid=10s`）动态解析，并在隔离栈上验证：后端换 IP 后前端无需重启。

### 2.1 当前实际部署形态（2026-11-10 核实）

负责人已决定**暂不迁移**数据库到群晖，当前生产形态如下：

| 层 | 目标架构 | 当前实际 |
| --- | --- | --- |
| 应用层 | DGX Spark | DGX Spark（一致） |
| 数据库层 | 群晖 Container Manager 中的 PostgreSQL | **DGX Spark 本机 Docker**：容器 `digidocs-postgres`，镜像 `pgvector/pgvector:pg17-trixie`，数据卷 `digidocs-mgt_postgres_data`，后端经 compose 网络连接 `postgres:5432` |
| 文件层 | 群晖 DSM / File Station | 群晖 DSM / File Station（一致） |
| 数据库备份 | 群晖 | 每日 03:30 在 DGX Spark 本机 `pg_dump`，再由 `digidocs-backup-sync` 同步一份到群晖 |

影响与注意：

- 数据库与应用同机，查询无跨机网络延迟；但 DGX Spark 单机故障会同时影响应用与数据库，恢复依赖群晖上的备份副本。
- 将来迁移到群晖时，群晖侧必须使用同一 pgvector 镜像，否则语义检索自动关闭（见第 3.2 节「语义检索」）；迁移前需评估群晖内存（HNSW 索引与 PostgreSQL 常驻内存）与经局域网访问的查询延迟，并做一次 `pg_dump` 恢复演练。

## 3. 仓库内部署资产

- 根目录 [docker-compose.yml](../docker-compose.yml)
  - 启动 `postgres`、`backend-go`、`backend-py-worker`、`frontend`
- 根目录 [.env.example](../.env.example)
  - 本地开发模板
- 根目录 [.env.production.example](../.env.production.example)
  - 部署模板
- 前端镜像 [frontend/Dockerfile](../frontend/Dockerfile)
- 前端反向代理 [frontend/nginx/default.conf](../frontend/nginx/default.conf)
  - 当前生产口径（2026-08-17 调整）：
    - `/api/` 用 `location ^~` 转发到 `backend-go`。**必须是 `^~` 而不是普通前缀匹配**，否则会被下面的扩展名正则抢走——git 远端地址 `/api/v1/git/<slug>.git` 正好以扩展名结尾，一旦被当成静态文件匹配，git clone/push 会整体失效；
    - `/assets/`、`/index.html`、`/favicon.ico` 仅在文件真实存在时返回；
    - 带文件扩展名的路径（正则 `\.[a-zA-Z0-9]+$`）只查真实文件，缺失即 `404`，不回退 shell——缺失的静态资源应当以静态资源的方式失败；
    - 其余路径统一返回 SPA shell，由 Vue Router 决定渲染内容（含前端自带的品牌化 404 页）。
    - 早期写法是「一条路由一个 `location =` 块」。它同样能挡住扫描，但**新增页面必须同步改 nginx，否则刷新即 404**，已经踩过一次；改成上面的口径后前后端路由表不再需要手工对齐。注意仍未使用 `try_files $uri $uri/ /index.html`：shell 是直接返回的，不会拿任意请求路径去磁盘上试探，因此原先规避 negative dentry / slab 增长的目的依然成立。
  - **安全响应头**：`server_tokens off`（不再回显 nginx 版本号），并统一下发 `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: same-origin`。当前公网入口为纯 HTTP，因此**刻意不下发 HSTS**——没有 TLS 时下发 `Strict-Transport-Security` 会把客户端锁在打不开的 https 上；等 443 入口落地后再一并加上。
  - **请求体上限**：`client_max_body_size 512m` 只是粗粒度外层边界，真实的分接口上限在 backend-go（见 API 设计 11.3）。该值需保持大于等于后端最大上限，否则超限上传会返回 nginx 的通用错误页而不是 API 的可读 413。
  - **缓存口径**：`index.html` 及各 SPA 入口路由统一返回 `Cache-Control: no-cache`（每次校验），`/assets/` 哈希资源保持 `immutable` 长缓存。
    - 原因：前端每次重新构建会给分块换哈希名并删除旧文件；若 `index.html` 被浏览器缓存，部署后老页面会请求已删除的旧分块（404）导致懒加载路由（如「代码」）打不开。`no-cache` 让浏览器始终拿到最新分块引用，彻底规避"部署后需手动强刷"问题。

## 3.1 烟测隔离栈（不要用演示环境跑烟测）

烟测会往目标库写入一次性数据：`smoke%` 文档版本、「请用一句话确认 smoke 已打通」会话、`@digidocs.test` 注册账号、邀请链接。此前 `smoke-local.sh` 默认打 `127.0.0.1:18081`（就是演示后端），`smoke-e2e.sh` 还会把 `seed.sql` 重新灌进演示库，等于每跑一次烟测就污染一次客户演示内容、并重置演示账号。

现在烟测有自己的栈，定义在 [docker-compose.smoke.yml](../docker-compose.smoke.yml)：

| 维度 | 演示栈 | 烟测栈 |
| --- | --- | --- |
| compose project | `digidocs-mgt`（默认） | `digidocs-smoke` |
| 容器名 | `digidocs-*` | `digidocs-smoke-*` |
| PostgreSQL | 15432 / `digidocs_mgt` | 15433 / `digidocs_smoke` |
| 后端 | 18081 | 18083 |
| 前端 | 18080 | 18082 |
| 网段 | `172.29.0.0/24` | `172.30.0.0/24` |
| 存储 | `synology`（真实 NAS） | `memory`（不碰群晖） |
| `APP_ENV` | `production` | `smoke` |

常用命令：

```bash
make smoke-e2e          # 起栈 → 灌种子 → 烟测 → 销毁，一条命令跑完
make smoke-stack-up     # 只起栈（反复调试时用）
make smoke              # 对已起的栈跑接口烟测
make smoke-stack-down   # 销毁（含数据卷）
```

两条护栏：

- `smoke-local.sh` 在写任何数据之前会请求 `/api/v1/system/info` 校验对端 `APP_ENV=smoke`，打到演示/生产环境直接 abort。确需对共享环境跑时显式 `ALLOW_SMOKE_ON_SHARED=1`，跑完用 `make clean-demo-data-apply` 清理。
- `docker-compose.smoke.yml` 里三处 `ports` 都带 `!override`。**不要去掉**：compose 默认把 `ports` 列表追加合并，去掉后烟测栈会连演示栈的 18081/18080/15432 一起绑，直接和正在运行的演示环境撞端口。

已知限制：**worker 默认不随烟测栈启动**。它要访问宿主机上的 OpenClaw 网关，而容器访问宿主机走宿主机 INPUT 链、本机 UFW 默认 DROP 且只放行了演示栈的 `172.29.0.0/24`。要跑 assistant 烟测（`RUN_ASSISTANT_SMOKE=1`），先为 `172.30.0.0/24 → 172.29.0.1:18789` 对应的烟测网段补一条 UFW 放行规则；未放行时症状是 60s 静默超时而不是连接被拒，排查入口 `grep "UFW BLOCK" /var/log/ufw.log`。

## 3.1.1 真实客户端 IP 当前拿不到（影响限流与审计）

**实测结论**：公网连发 12 次登录、每次带不同的 `X-Forwarded-For`，全部被计入同一个桶，第 11 次即 429。原因是公网流量经 frp **裸 TCP** 隧道进来，nginx 对每个访问者看到的 `remote_addr` 都是 `172.29.0.1`（docker 网关），真实客户端地址在到达应用层之前就已经丢了。`TRUSTED_PROXY_DEPTH` 调成任何值都救不回来。

后果是反的：它并没有让攻击者比别人更受限，反而让任何一个用户（或攻击者）耗光共享额度后，把**其他所有人**挡在门外一分钟。

已做的应对（应用层）：登录限流改为按**被尝试的账号**分桶（`middleware.LoginIdentifierKey`），这样爆破被限制在目标账号上，不再连坐其他用户。实测：猛攻账号 A 到 429 的同时，账号 B 登录正常、真实账号登录 200。

**要真正拿回客户端 IP，需要改基础设施**（不在本仓库范围）：

1. frp 侧给该 proxy 开启 PROXY protocol：`transport.proxyProtocolVersion = "v2"`（frpc.toml）；
2. nginx 侧改为 `listen 80 proxy_protocol;`，并配置 `set_real_ip_from <frp 来源网段>;` 与 `real_ip_header proxy_protocol;`；
3. 两步都生效后，再按实际代理链设置 `TRUSTED_PROXY_DEPTH`。

在此之前，`audit_events.ip_address` 即使写入也只会记录到 `172.29.0.1`，没有取证价值——这也是该字段目前留空的原因之一。

## 3.2 上线运维基线（备份 / 健康检查 / 日志）

### 备份

`scripts/codex/backup.sh` 备份两样「丢了就没有了」的东西：PostgreSQL 全库，以及 `code_repos` 卷里的 Git 裸仓库（成员推送代码的唯一副本）。群晖上的文件由 DSM 自身的快照/备份能力负责，`.env` 含密钥需单独保管，两者都不在本脚本范围内。

**本地备份只防人祸（2026-08-19 前的状态）**：`postgres_data` 卷和 `$BACKUP_DIR` 在同一台宿主机的同一块盘上，磁盘物理损坏或整机故障会同时带走源数据和全部备份历史。现在本地校验通过后会额外把两个文件同步一份到群晖 NAS（异盘、异机）：复用 `backend-go` 容器已经配置好的 `SYNOLOGY_*` 凭据（应用本身就用它做文件存储，不引入新凭据），通过 `backend-go/cmd/backup-sync`（新增的小工具，复用 `internal/storage/synology` 客户端）以 `docker cp` + `docker exec` 的方式推送，存在 NAS 的 `ops-backups/` 目录下，与应用自己的 `documents/`、`data-assets/` 分开。默认要求群晖配置存在且同步成功；只需本地备份的部署必须显式设置 `DIGIDOCS_OFFSITE_REQUIRED=0`。全部待传副本完成验证后才按 `BACKUP_KEEP_DAYS` 清理旧文件，NAS 清理仅匹配本工具生成的备份文件名；清理失败只警告，上传或下载校验失败则让整个脚本以非零状态退出。

```bash
./scripts/codex/install-backup-timer.sh   # 安装 systemd 用户级 timer，默认每天 03:30
systemctl --user list-timers digidocs-backup.timer
```

保留 14 天（`BACKUP_KEEP_DAYS` 可调），`Persistent=true` 保证关机错过的那次开机后补跑。脚本会校验导出结果的大小、gzip 完整性和是否含建表语句——一份空的或截断的备份比没有备份更危险，因为它会让人以为自己有备份。

备份恢复与保留约定（2026-10-08）：

- `backup-sync upload` 上传后重新下载并核对字节数及 SHA-256；`verify <local-file> <remote-key>` 只读核对已有副本。上传响应成功本身不算异地验证成功。
- `backup.sh` 使用目录内的 `flock` 锁防止并发，临时备份校验后才原子改名。每次扫描未确认的历史备份，先验证 NAS 已有副本，不匹配或不存在时补传；已确认文件以 `.offsite/` 中的摘要及目标标记记录，不保存凭据。
- 未确认副本不能被本地保留策略删除；任一文件同步失败时暂停本轮本地及 NAS 清理，保留失败状态。后端容器停止也算同步失败。默认必须完成异地同步；确实只需本地备份的部署必须显式设置 `DIGIDOCS_OFFSITE_REQUIRED=0`，不能通过缺少配置静默降级。
- `backup.sh --sync-only` 只补传和验证现有备份，不生成新备份、不清理。首次升级会核对所有存量副本并建立确认标记；断网恢复后可直接用此命令补传。
- Synology HTTP 错误在存储适配层去除完整 URL 查询串及 URL 用户信息，避免密码和会话 ID 进入日志；DSM 错误码和底层超时类型仍保留。
- 密码轮换在 DSM 完成后，通过受控终端编辑部署 `.env` 的 `SYNOLOGY_PASSWORD`，再重建 `backend-go`；不要把密码粘贴到聊天、命令行参数或工单。轮换共用账号需同步所有使用者，历史泄露密码不能作为回滚目标。

回滚时恢复旧 `backup.sh` 和发布前保留的后端镜像，保留所有备份和 `.offsite/` 标记；凭据继续使用新密码。新增验证失败会让备份服务失败退出，告警不能用 `reset-failed` 代替修复。

**恢复演练是验收项，不是可选项。** 做法是把最新的 `db_*.sql.gz` 灌进一个一次性 postgres 容器，核对关键表行数与源库一致：

```bash
# 只选一份已校验的备份，不要把多个历史 SQL 直接拼接恢复。
backup_file="$(find "$HOME/ops/digidocs-backups" -maxdepth 1 -name 'db_*.sql.gz' | sort | tail -n 1)"
docker run -d --rm --name restore-test --network none \
  --tmpfs /var/lib/postgresql/data:rw,size=512m \
  -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=restore_check postgres:17
# 等 pg_isready 成功后再导入；演练结束删除一次性容器。
docker exec restore-test pg_isready -U postgres -d restore_check
zcat "$backup_file" | docker exec -i restore-test psql -X -v ON_ERROR_STOP=1 -U postgres -d restore_check
# 核对表行数与内容摘要后执行：docker rm -f restore-test
```

依赖 `loginctl show-user <user> --property=Linger` 为 `yes`，否则未登录时用户级 timer 不会触发。

### 健康检查

四个服务都配了 `healthcheck`，`depends_on` 改为 `condition: service_healthy`。原因是 `restart: unless-stopped` 只能处理**进程退出**，处理不了**进程还在但卡死**（连接池耗尽、群晖调用挂住）。

- backend-go / frontend：探 HTTP。**必须写 `127.0.0.1` 而不是 `localhost`**——容器内 `localhost` 先解析到 `::1`，而 nginx 的 `listen 80` 和 Go 的 `:8080` 都只绑 IPv4，用 `localhost` 会得到 `Connection refused`，把完全正常的服务判成 unhealthy（本项目踩过）。backend-go 镜像为此装了 `curl`（debian-slim 既无 curl 也无 wget）；前端用 busybox wget，超时参数是 `-T` 不是 `--timeout`。
- worker：不监听端口，没有可探测的 HTTP 面。它每轮轮询刷新 `/tmp/digidocs-worker-heartbeat`，健康检查测心跳新鲜度，超过 6 倍轮询间隔即判定轮询循环卡死。

### 日志

四个服务统一 `json-file` + `max-size: 10m` + `max-file: 3`。json-file 默认**不轮转**，而后端对每个请求打一行访问日志、worker 每 5 秒轮询一次，不封顶就是慢性占满磁盘。宿主机 journald 的 2G 上限管不到这部分。

### 资源限制（2026-08-19 新增）

四个服务此前都没有 CPU/内存上限。这台机器往往同机部署 OpenClaw/vLLM 推理容器，任何一个服务失控（比如 worker 处理超大扫描件 OCR 时内存暴涨）都能挤占同机其它服务的资源，而且没有边界。现通过 `deploy.resources.limits` 给四个服务分别设了上限（Compose V2 在非 swarm 模式下同样生效，不需要 `docker stack deploy`）：

| 服务 | CPU 上限 | 内存上限 | 理由 |
| --- | --- | --- | --- |
| postgres | 2.0 | 2g | 当前数据量小，留够常规查询/索引维护的余量 |
| backend-go | 2.0 | 1g | 无状态 HTTP API，内存占用可预期 |
| backend-py-worker | 4.0 | 4g | 明显比其它三个宽松：`pdftoppm`/`tesseract` 处理大扫描件的内存峰值没有实测过精确上限，限制太紧会把正常大文件处理直接 OOM，比不限制更糟；`MAX_OCR_PAGES`（见下）已经从任务层面兜了底，这里的宽松内存上限是第二道防线 |
| frontend | 1.0 | 256m | 纯静态文件由 nginx 提供，占用很低 |

这些数值按当前实测用量（四个服务空闲时都是个位数 MB）给了充足但不放任的上限，不是精确压测出的下限；后续如果 worker 处理大文件时真的触顶 OOM，优先加大 `backend-py-worker` 的内存上限，而不是直接取消限制。

### Worker 并发与 OCR 上限（2026-08-19 新增）

**并发**：Worker 此前严格单线程串行处理任务——一批最多 10 个（Go 侧 `PollTasks` 的硬编码 `limit`），单任务耗时上限可达 `OPENCLAW_TIMEOUT_SECONDS`（默认 180s）甚至更久，极端情况下一批任务能堵住 30 分钟以上，而 Go 队列消费用的是 `SELECT ... FOR UPDATE SKIP LOCKED`，天然支持多消费者并发领取，这个能力此前完全没被用上。现在 `dispatcher.run_forever`/`poll_once` 用 `WORKER_CONCURRENCY`（默认 3）个线程并发处理同一批任务，等这批全部处理完才去拉下一批——不是把整个轮询循环改成流式，只是把"一批内部的处理"从串行改成并发。各任务处理路径本身无共享可变状态（OpenClaw/回调/上下文客户端都是无状态封装），单任务崩溃仍然互相隔离。

**OCR 页数上限**：扫描 PDF 的自动 OCR 之前没有页数上限，`SUBPROCESS_TIMEOUT_SECONDS` 只约束单页 `tesseract` 调用，一份 100 页的扫描件理论上能让处理它的线程跑上几小时，且任何有上传权限的课题成员都能触发。现在 `MAX_OCR_PAGES`（默认 30）会在渲染阶段就用 `pdftoppm -l MAX_OCR_PAGES+1` 只多渲染一页去探测"是否超限"，一旦超限直接报错拒绝，不会先跑完整份 OCR（包括渲染其余页面和逐页识别）再报错。

### 迁移

迁移是启动硬依赖：迁移目录找不到或迁移执行失败，`BuildContainer` 直接返回错误、进程起不来。此前是打一条 warning 然后继续启动，等于让应用跑在旧的或半截的 schema 上——表现为零星 500，或者更糟的是写入静默错位，而没人会去翻启动日志。宁可起不来也不要带病运行；容器重启策略会自动重试，真正坏掉的迁移会立刻可见。

## 5.1 最终 TLS / 反向代理 / 防火墙口径

推荐正式部署按下面口径收口：

1. TLS 终止层
   - 放在应用层主机（`DGX Spark`）入口反向代理；
   - 推荐由宿主机 Nginx / Caddy 统一监听 `443`；
   - `80` 只保留跳转到 `443`。
2. 反向代理转发
   - `/` -> `frontend` 容器（静态资源与前端路由）；
   - `/api/v1/` -> `backend-go:8080`；
   - `backend-py-worker` 不直接暴露给浏览器或外部网络；
   - OpenClaw 兼容 HTTP 端点仅保留给本机/内网服务访问，不作为公网入口。
   - 若前端仍由 Nginx 承载 SPA，不要继续使用 `location / { try_files $uri $uri/ /index.html; }` 这类“未知路径全量回退”写法作为公网默认模板；正式部署应改成：
     - 已知前端路由显式回退到 `/index.html`；
     - 静态资源只在真实存在时返回；
     - `/.env`、`/.git/config`、`/phpinfo.php`、随机扫描路径等未知路径直接 `404` 或更早拒绝；
     - 否则公网扫描会在 overlay/VFS 上持续制造 negative dentry，表现为 `Slab / SReclaimable` 异常升高，即使业务进程 RSS 本身并不高。
3. 应用层防火墙
   - 对用户侧只开放 `80/443`；
   - `22` 仅对运维管理网段开放；
   - `18080/18081` 这类容器调试端口不作为正式外部入口长期暴露。
4. 群晖侧防火墙
   - `5001`（DSM / File Station HTTPS）仅对应用层主机开放；
   - `5432`（PostgreSQL）仅对应用层主机开放；
   - DSM 管理入口与 SSH 仅对管理员网段开放，不对普通用户网段开放。
5. 网络约束
    - 用户浏览器永远只访问应用层反向代理，不直接访问群晖；
    - 应用层主机负责访问群晖 DSM / PostgreSQL；
    - 应用节点与群晖同局域网时，群晖 DSM / PostgreSQL 应优先走局域网静态 IP 或 DHCP 保留地址；
    - Tailscale 建议只用于远程 SSH、RustDesk、应急排障，不作为文件、数据库和 AI 主链路默认依赖；
    - 当前仓库的 compose 应用网络固定为 `172.29.0.0/24`，避免 Docker 每次重建时漂移到新的桥接子网；
    - 若继续使用 Tailscale，需确保 `table 52` 至少对 `172.17.0.0/16`、`172.18.0.0/16`、`172.29.0.0/24`、`192.168.1.0/24` 写入 `throw` 路由，避免覆盖 Docker 网桥与本机局域网回流；
    - `./scripts/codex/install-persistent-routing.sh` 会安装对应的 `tailscaled` 持久化修复脚本，并保留额外例外网段（如 `8.152.204.76/32`）的注入口径。

## 6.1.2 持久化路由修正

当前仓库已提供 Linux 宿主机持久化安装入口：

```bash
./scripts/codex/install-persistent-routing.sh
```

该安装动作会完成：

1. 把仓库内 `ops/systemd/digidocs-route-fix.sh` 安装到 `/usr/local/bin/digidocs-route-fix.sh`
2. 把 `ops/systemd/tailscaled-digidocs-routing.conf` 安装到 `/etc/systemd/system/tailscaled.service.d/digidocs-routing.conf`
3. 安装并启用 `digidocs-route-fix.service` / `digidocs-route-fix.timer`
4. `systemctl daemon-reload`
5. 立即执行一次路由修正脚本，确保当前会话生效

安装后的持久化机制：

- 每次 `tailscaled` 启动或重启后，都会自动执行 `/usr/local/bin/digidocs-route-fix.sh`
- `digidocs-route-fix.timer` 每 2 分钟执行一次同一脚本，兜底处理 `tailscaled` 在运行期刷新 `table 52` 的情况
- 目标是始终保持以下规则存在于 `table 52`：
  - `throw 8.152.204.76`
  - `throw 172.17.0.0/16`
  - `throw 172.18.0.0/16`
  - `throw 172.29.0.0/24`
  - `throw 192.168.1.0/24`

建议安装后执行：

```bash
systemctl show tailscaled --property=DropInPaths --no-pager
systemctl list-timers digidocs-route-fix.timer --no-pager
ip route show table 52
sudo systemctl restart tailscaled
ip route show table 52
```

若重启 `tailscaled` 后上述 `throw` 规则仍在，则说明持久化配置已生效。

补充说明：

- 当前脚本会在短时间内重复回写几轮 `throw` 路由，以覆盖 `tailscaled` 启动后延迟补写 `table 52` 的窗口；
- 若 `tailscaled` 在运行中因网络切换或 DERP/出口变化重新写入 `table 52`，timer 会在最多约 2 分钟内再次修正；
- 已在当前开发机验证通过，无需再手工执行 `ip route replace throw ... table 52`。

## 6.1.3 前端 18080 / 后端 18081 访问超时排查

若通过 RustDesk 登录远程桌面后，浏览器访问 `http://127.0.0.1:18080` 或 `http://127.0.0.1:18081/healthz` 超时，但容器本身仍在运行，优先按本节排查宿主机路由表。

典型现象：

1. `docker compose ps` 显示 `frontend`、`backend-go` 等容器均为 `Up`；
2. `ss -ltnp` 能看到宿主机正在监听 `0.0.0.0:18080` / `0.0.0.0:18081`；
3. 容器内访问前端或后端正常；
4. 宿主机或 RustDesk 桌面浏览器访问 `127.0.0.1:18080` 超时。

优先检查 `tailscaled` 的 `table 52` 是否重新接管了 Docker 网桥或局域网网段：

```bash
ip route show table 52 | grep -E 'throw 8\.152\.204\.76|throw 172\.17\.0\.0/16|throw 172\.18\.0\.0/16|throw 172\.29\.0\.0/24|throw 192\.168\.1\.0/24'
```

期望能看到以下规则：

```text
throw 8.152.204.76
throw 172.17.0.0/16
throw 172.18.0.0/16
throw 172.29.0.0/24
throw 192.168.1.0/24
```

若没有输出，或看到 `172.17.0.0/16` / `172.18.0.0/16` 继续指向 `tailscale0`，则说明 Tailscale 路由表重新覆盖了 Docker / 局域网回流规则。此时先执行一次已安装的修复脚本：

```bash
sudo /usr/local/bin/digidocs-route-fix.sh
```

若当前机器尚未安装到 `/usr/local/bin`，可在仓库根目录临时执行：

```bash
sudo DIGIDOCS_ROUTE_FIX_ATTEMPTS=1 ops/systemd/digidocs-route-fix.sh
```

修复后验证：

```bash
curl -I http://127.0.0.1:18080
curl -I http://127.0.0.1:18081/healthz
ip route show table 52
```

如果问题在 `tailscaled` 重启、网络切换、Docker 网络重建后反复出现，先确认持久化安装仍在：

```bash
systemctl show tailscaled --property=DropInPaths --no-pager
systemctl list-timers digidocs-route-fix.timer --no-pager
sudo ./scripts/codex/install-persistent-routing.sh
```

当前持久化方案通过 `tailscaled` 的 systemd drop-in 在服务启动或重启后自动执行修复脚本，并通过 `digidocs-route-fix.timer` 做运行期兜底。

## 6.1.4 同一局域网用户访问方式

本地 compose 联调时，前端容器默认暴露在宿主机 `18080`，后端 Go API 默认暴露在宿主机 `18081`。同一局域网内其他用户访问时，应使用宿主机局域网 IP，而不是 `127.0.0.1`。

当前开发机示例：

```text
http://192.168.1.142:18080
```

使用前确认：

```bash
hostname -I
docker compose ps
ss -ltnp | grep -E ':18080|:18081'
curl -I http://127.0.0.1:18080
curl -I http://127.0.0.1:18081/healthz
```

说明：

- `127.0.0.1:18080` 只代表访问者自己机器上的端口，不能给同网段其他用户使用；
- 同网段用户应访问 `http://<宿主机局域网IP>:18080`；
- 若目标机器开启防火墙，需要允许局域网访问 TCP `18080`，后端 `18081` 建议只在联调时暴露；
- 正式部署仍建议通过反向代理和域名入口访问，不长期暴露 `18080/18081` 作为生产入口。
