# DigiDocs 部署与运行参考

首次客户安装按[现场部署手册](现场部署逐条清单.md)执行。本页供部署负责人和运维人员查询入口、备份、升级、回退及故障排查。模型端点、密钥字段及服务默认配置分别以 [生产环境模板](../.env.production.example)和 [Compose 文件](../docker-compose.yml)为准。

## 部署边界

| 组件 | 标准位置与职责 |
| --- | --- |
| DGX Spark 与 Docker Compose | `frontend`、`backend-go`、`backend-py-worker` 和 `postgres`。Go 在启动时执行迁移。PostgreSQL 17 使用 Compose 固定摘要的 pgvector 镜像，数据库卷与 Git 裸仓库卷持久化。 |
| 群晖 DSM | File Station 文件服务、文档及数据对象快照、数据库与 Git 的异机副本。 |
| 模型端点 | 由客户指定的 OpenAI 兼容网关，可用本地模型服务或 OpenClaw Gateway。Worker 需要从容器内访问 `/v1/chat/completions`；仅检查 `/v1/models` 无法验收业务。 |
| 正式入口 | 客户域名的 HTTPS 代理，转发到 DGX 的 `127.0.0.1:18080`。后端、数据库及前端调试端口默认仅绑定回环。 |

标准拓扑与现有 DGX 验证环境一致。独立数据库节点属于客户特定拓扑，须另行确认 pgvector、传输保护和备份脚本适配；仓库的部署后检查与定时备份默认使用本机 Compose 数据库。

## HTTPS 入口样例

将域名和证书文件改成客户 IT 提供的真实值。以下片段用于 DGX 宿主机的 Nginx 站点配置，由客户 IT 合并到现有配置。

```nginx
server {
    listen 80;
    server_name docs.example.org;
    return 301 https://docs.example.org$request_uri;
}

server {
    listen 443 ssl;
    server_name docs.example.org;
    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;
    client_max_body_size 512m;

    location / {
        proxy_pass http://127.0.0.1:18080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 300s;
    }
}
```

该样例是宿主机入口加容器内前端 Nginx，共两层受控代理，适用 `TRUSTED_PROXY_DEPTH=2`；增加负载均衡或隧道时由 IT 验证真实客户端地址后调整。容器内代理以自身连接协议转发，当前页面生成的 Git remote 可能是 HTTP；实际验收和操作以正式 HTTPS URL 为准。预览与文件传输只经应用入口。

## 备份和恢复

备份安装、启用与首次运行见[现场部署手册](现场部署逐条清单.md)。备份脚本默认取本机 `digidocs-postgres` 的数据库及 `digidocs-mgt_code_repos`，写至运维账号的 `~/ops/digidocs-backups`，再传至群晖 `ops-backups/` 并回读校验 SHA-256。默认周期每天 03:30、保留 14 天。保留策略在异机同步失败时暂停。NAS 对象的快照和秘密配置由客户各自的机制备份。

恢复演练选取同一恢复点的 SQL、Git 归档和 NAS 快照。数据库恢复到网络隔离的一次性 PostgreSQL，镜像使用与生产一致的 pgvector 摘要。以下命令在生产 DGX 上只读取当前镜像 ID，用它启动隔离数据库。先填写已校验的备份名。

```bash
restore_sql="$HOME/ops/digidocs-backups/<填写数据库备份文件名>.sql.gz"
restore_image=$(docker inspect -f '{{.Image}}' digidocs-postgres)
docker run -d --name digidocs-restore-check --network none \
  --tmpfs /var/lib/postgresql/data \
  -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=restore_check "$restore_image"
docker exec digidocs-restore-check pg_isready -U postgres -d restore_check
# 上一步显示 accepting connections 后执行
set -o pipefail
gzip -dc "$restore_sql" | docker exec -i digidocs-restore-check \
  psql -X -v ON_ERROR_STOP=1 -U postgres -d restore_check
docker exec digidocs-restore-check psql -X -U postgres -d restore_check \
  -c 'SELECT count(*) FROM document_versions; SELECT count(*) FROM code_repositories WHERE NOT is_deleted;'
```

将 Git 归档解压到隔离目录，按启用的仓库记录核对裸仓库及提交。由 NAS 管理员恢复快照到单独共享目录，并在隔离应用里抽测版本下载、SHA-256 和 Git 克隆。演练完成后移除一次性容器。真实恢复需确定共同恢复点后另行执行。

## 升级与回退

1. 记录现用 Git 提交、镜像 ID、迁移和客户启用的功能。先完成数据库、Git 与 NAS 备份，保存上一版镜像标签及受限配置副本。
2. 在隔离栈验证批准的新版本。安排窗口再切换源码，使用 `docker compose --profile app up -d --build --wait --wait-timeout 180`，Go 与 Worker 同批更新。
3. 经正式域名运行 `PUBLIC_URL=https://docs.example.org make post-deploy-check`，抽验登录、下载及约定业务。脚本核对容器健康、三处迁移清单及前端路径。
4. 回退时使用已保留的兼容镜像。若版本间数据库不兼容，由负责人在隔离环境验证恢复点后再执行数据回退。关闭语义检索可清空 `EMBEDDING_BASE_URL` 并重建 Go，保留 pgvector 结构。

## 常见故障定位

| 现象 | 先检查 |
| --- | --- |
| 容器反复启动或迁移失败 | `docker compose logs --tail=100 backend-go postgres`。检查 PostgreSQL 镜像、凭据和迁移报错，处理前保留持久卷。 |
| 页面打开但 API 失败 | `make post-deploy-check`，再用正式域名复验。依次看客户入口、前端代理、Go 就绪和数据库。 |
| 上传失败或超时 | 检查 DSM 地址、证书、服务账号权限、宿主机入口体积限制、带宽及 Go 容器临时盘空间。数据资产单文件上限 511 MiB，版本上传和 OCR 限制见[用户说明](用户使用说明.md)。 |
| Worker 健康异常或 AI 失败 | `docker compose logs --tail=100 backend-py-worker`。检查回调凭据一致、模型端点从容器可达、模型名和实际生成请求。 |
| 定时备份结果异常 | `journalctl --user -u digidocs-backup.service -n 50 --no-pager`，确认 linger、剩余空间、DSM 可达及 SHA-256 回执。 |
| 需要主动验证接口 | 在独立栈运行 `make smoke-e2e`。如需 AI，确认烟测网段到模型端点的访问后使用 `RUN_ASSISTANT_SMOKE=1 make smoke-e2e`。真实 NAS 临时目录预检使用 `RUN_SYNOLOGY_PREFLIGHT=1 make smoke-e2e`。 |

发布证据和现场遗留项在[优化清单](客户交付优化清单.md)。早期单机、Tailscale 和代理故障记录见[文档索引](INDEX.md)的历史资料。
